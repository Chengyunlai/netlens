# raw-network

从**最原始的角度**看一次 HTTPS 请求：不用 `node:http` 和 `node:https`，
自己拼 DNS 查询报文、自己做 TCP 连接、自己走 TLS 握手、自己写 HTTP 请求报文并解析响应。

这个阶段不产出工具，产出的是**可观察的知识**：每一层的字节、事件和时间都能打印出来。

## 最短启动命令

```bash
node examples/raw-network/user_code/main.ts www.jd.com
```

无需安装、无需构建：Node 22.18 起默认启用类型剥离，`.ts` 直接跑。

## 这四层各自要看什么

### 1 DNS：一个数据报出去，一个回来

| 现象 | 说明 |
| --- | --- |
| 查询 28 字节 / 响应 158 字节 | 查询报文小得惊人：12 字节头 + 域名编码 + 4 字节类型与类 |
| 没有握手 | UDP 是数据报协议，发出去就完了。代价是**不保证送达**，超时重传必须由应用层自己实现 |
| CNAME 链三跳 | `www.jd.com` 不是 A 记录，是一串别名。CDN 就是靠这个把用户调度到就近节点 |
| 名字压缩 | 响应里 4 条记录都复用了同一批域名字节（指针 `0xC0` 指回前面），否则 158 字节装不下 |
| TTL 550 / 304 | 每条记录各自有存活时间。TTL 归零前，再解析会拿到缓存 |

一个容易被忽略的点：解析结果里**每次返回的地址顺序可能不同**（DNS 轮询），
这是最朴素的一种负载均衡。

### 2 TCP：连接是一种操作系统资源

| 现象 | 说明 |
| --- | --- |
| `内核里的 fd 17` | 每条连接在内核里就是一个文件描述符。fd 耗尽（EMFILE）是生产环境里的真实故障 |
| 本地端口 52680 | 客户端端口由内核临时分配，它和四元组一起决定"这条连接"的身份 |
| 握手 11.8 ms | 三次握手至少一个 RTT。这个数字是所有网络延迟的基数 —— 任何跨网络的操作都至少付一次 |
| `setNoDelay(true)` | 关掉 Nagle 算法。它会把小包攒起来等 ACK，对吞吐友好、对交互式请求是灾难 |

### 3 TLS：握手本身就值一个往返

| 现象 | 说明 |
| --- | --- |
| 握手 97.2 ms ≈ 8 倍 RTT | 这一次数值偏高（见下面的实测对照）。理论上 TLS 1.3 只需 1 个 RTT |
| SNI = www.jd.com | 域名在**明文**阶段就发出去了，服务端据此决定回哪张证书。所以"加密的 HTTPS 不泄露访问域名"是错的 |
| ALPN = http/1.1 | 客户端提议协议列表，服务端挑一个。这个结果决定后面能不能用 HTTP/2 多路复用 |
| 证书链 2 级 | 叶子证书 `*.jd.com` 只被中间 CA 签，中间 CA 再被根 CA 签。**根证书不在链里**，它必须预先装在客户端 |
| 证书有效期 | 观察 `2025-11-24 → 2026-12-20`：证书过期是所有 HTTPS 服务最常见的故障 |

### 4 HTTP：TCP 是字节流，没有消息边界

这是整个实验里最值得看的一层。同一份输出里能看到两种截然不同的切分方式：

| 站点 | 读取次数与字节数 | 说明 |
| --- | --- | --- |
| www.jd.com（19 万字节） | 13 次，前 12 次各 16384 字节 | 单次 read 的上限由内核接收缓冲区决定。16384 = 16 KiB，**与 HTTP 协议无关** |
| neverssl.com（约 4 KB） | 1 次，4268 字节 | 响应头和整个正文在**同一次 read** 里到达 |

两次都证明同一件事：**一次 `data` 回调拿到多少字节是偶然的**。
客户端必须能处理任意切分 —— 头可能只到一半（半包），也可能头和正文一起来（粘包）。

响应体什么时候结束，HTTP/1.1 给了三条规则，这个实现三条都处理了：

1. `Content-Length: N` —— 数够 N 个字节
2. `Transfer-Encoding: chunked` —— 每个分片自带长度，遇到 0 号分片结束
3. 都没有 —— 读到连接关闭为止

## 实测对照：TLS 1.3 与 1.2 差在哪里

`--tls12` 参数把版本上限压到 1.2，同一条链路各跑 5 次（www.jd.com，同一台机器）：

| 运行 | TCP 握手（≈ RTT） | TLS 1.3 握手 | TLS 1.2 握手 |
| --- | --- | --- | --- |
| 1 | 10.9 / 14.1 | 19.4 | 43.6 |
| 2 | 12.4 / 11.6 | 29.2 | 30.2 |
| 3 | 9.8 / 12.4 | 19.4 | 27.3 |
| 4 | 10.3 / 9.6 | 17.6 | 29.0 |
| 5 | 11.5 / 14.1 | 22.0 | 73.6 |
| **中位数** | 10.9 / 12.4 | **19.4** | **29.0** |

**中位数之差 = 9.6 ms，而这条链路的 RTT 中位数是 10.9–12.4 ms。**

也就是说，TLS 1.2 比 1.3 多花的那段时间，约等于**整整一个往返** ——
这与"TLS 1.3 握手 1 个 RTT、1.2 需要 2 个 RTT"完全吻合。

> 测量说明：5 次里有 1 次 73.6 ms 的离群值（网络抖动），所以结论建立在中位数上，
> 单次读数不足以支撑任何判断。

对比过程中还观察到两件值得记下的事：

- **baidu.com 无论是否限制版本都协商成 TLS 1.2** —— 服务端不支持 1.3。
  "客户端支持 TLS 1.3" 不等于 "这条连接会用 TLS 1.3"。
- **example.com（Cloudflare）的对比数据被丢弃**：该链路 TCP 握手在 170 ms 到 4200 ms 之间抖动，
  噪声远大于要测的信号，在这种条件下得出的任何差值都不可信。

## 明确不验证什么

- **不做性能评分**，也不给优化建议 —— 那是 `probe` 阶段的事。
- **不实现 HTTP/2 或 HTTP/3**。ALPN 只提议 `http/1.1`，因为 `node:tls` 之上没有 HTTP/2 帧编解码。
- **不实现 TCP 回退**。DNS 响应被截断（TC=1）时只报告，不改用 TCP 53 端口重查。
- **不处理 IPv6**。只查 A 记录，不查 AAAA，也不做双栈并发（Happy Eyeballs）。
- **不评估 DNS 缓存命中**。每次都直接问服务器。
- **不测量真实丢包与重传**。应用层看不到 TCP 重传，需要抓包。

## 调用路径

从入口到真实结果，一次探测经过的稳定符号：

```text
user_code/main.ts  main()
  → core/dns.ts    resolve() → buildQuery() → ask() → parseResponse() → readName()
  → core/tcp.ts    connectTcp()
  → core/tls.ts    handshake() → readChain()
  → core/http-raw.ts  speakHttp() → ingest() → decodeChunked()
```

分层原则：**每层只通过参数把结果交给下一层**，没有共享状态。
想换成自己写的 HTTP 解析，只动第四层；想加 QUIC，不用碰前三层。

## 关键观察点

调试和阅读时值得停下来看的地方（用符号定位，不要用行号 —— 行号会漂移）：

| 位置 | 看什么 | 预期 |
| --- | --- | --- |
| `dns.readName` | `(length & 0xc0) === 0xc0` 分支 | 进入说明遇到了压缩指针，`hops` 单调递增 |
| `dns.readResolvers` | 读出来的服务器地址 | 应与 `scutil --dns` 一致；不一致是 macOS 的已知行为 |
| `dns.ask` | 超时回调 | UDP 没有内置重传，这个定时器是唯一的兜底 |
| `tcp.connectTcp` | `_handle.fd` | 每次运行都不同，但同一进程内单调变化 |
| `tls.handshake` | `maxVersion` 参数 | 设成 `TLSv1.2` 后，握手耗时增加约一个 RTT |
| `tls.readChain` | `issuerCertificate` 链 | 自签名证书会在这里遇到"自己签自己"，靠 `seen` 集合跳出 |
| `http.speakHttp` | `reads` 数组 | 大响应上会看到反复出现同一个数（接收缓冲区大小） |
| `http.ingest` | 第一次 `separator < 0` | 表示响应头还没收全，数据被留在缓冲区里等下一批 |
